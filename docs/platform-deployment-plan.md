# Platform deployment plan

The install promise of this project is one command: `make up` on a host you
own. `deploy-railway.md` shows what that promise costs on a managed platform — a
dozen services wired by hand, four settings that fail silently, and a password
hash generated on another machine. This document plans how to get back to
*one step* on the platforms people actually reach for, and says plainly which
ones cannot host open-shield at all.

It is a plan, not a guide. Nothing here is implemented yet; each phase in §6
ends in a file in the repository and a worked deployment document like
`deploy-railway.md`.

---

## 1. What a platform must provide

open-shield is three long-running processes and two datastores. A platform can
host it only if it offers every row below. The last two are what separate a
deployment that filters from one that only appears to.

| Requirement | Why |
|---|---|
| Long-running containers | OpenResty holds keepalive connections to the engine; the engine runs the single audit writer goroutine (`internal/audit/writer.go`). Neither survives a request-scoped runtime. |
| Private network between services | The engine answers `/v1/decide` and `/v1/audit` without authentication. It must never have a public address. |
| PostgreSQL and Redis | The hash chain and the sliding-window rate limit. |
| One public ingress for the proxy, one for the dashboard | Everything else stays private. |
| A client-address header the edge **overwrites** | `ipblock`, `ratelimit` and the sign-in throttle key on it. A header the client can extend is a forged address (see `OS_TRUSTED_PROXY` in `deploy/.env.example`). |
| An origin reachable only privately | An origin with its own public URL bypasses every rule in the chain. |

### Not hostable: Vercel, Netlify, Cloudflare Pages

These are static-site and serverless-function platforms. Functions are
request-scoped, have no persistent process, cannot run OpenResty, and offer no
private network between services. There is nowhere to put the engine or its
single writer, and running the writer per invocation would fork the chain —
the one failure the forensic log exists to rule out.

What they *can* host is the protected application's own static frontend, with
its API base URL pointed at the proxy's domain. That is a supported topology —
it is exactly how the frontend sits outside the filter in `deploy-railway.md` —
but it is not a deployment of open-shield, and this plan does not pursue one.

## 2. The four portable settings

Every managed topology reuses the same four settings `deploy-railway.md`
introduced. Only their values change per platform:

| Setting | Decides | Per platform |
|---|---|---|
| `OS_LISTEN_PORT` / `PORT` | the port the proxy binds | injected by the platform |
| `OS_RESOLVER*` | how OpenResty resolves private names | depends on whether private DNS is IPv4, IPv6 or both |
| `OS_TRUSTED_PROXY` | which peers may set the client address | the edge's address range |
| `OS_REAL_IP_HEADER` | which header carries it | the header the edge overwrites |

**The last two are always measured, never copied from documentation.** The
Railway range was read off the proxy's own access log, and the header the
platform documented as safe turned out not to be set at all. Each phase below
repeats that measurement before its document is written.

## 3. Railway: from guide to template

Railway templates describe a whole project — services, datastores, variables
and the references between them — and deploy it from one button. The manual
steps in `deploy-railway.md` §4 map onto a template almost one to one.

### 3.1 What the template contains

- `postgres` and `redis` from the catalogue.
- `engine` from `engine/Dockerfile`, no public domain, health check `/readyz`.
- `dashboard` from `dashboard/api/Dockerfile`, public domain on `8081`, health
  check `/healthz`.
- `proxy` from `/proxy`, public domain on `80`, health check
  `/__openshield/health`.
- Every variable of `deploy-railway.md` §4, with service references
  (`${{Postgres.DATABASE_URL}}`, `engine.railway.internal`) filled in, and
  `OS_RESOLVER_IPV6=on`, `OS_TRUSTED_PROXY=100.64.0.0/10`,
  `OS_REAL_IP_HEADER=X-Forwarded-For`, `OS_SECURE_COOKIES=true` preset.
- `OS_SESSION_SECRET` generated by the template itself (Railway's template
  secret-generation function; confirm its current name before publishing).

### 3.2 What the person deploying still provides

Three inputs, asked for by the template:

1. **`OS_BACKEND_URL`** — the private address of the application to protect.
   The template cannot contain the origin: it is the user's own service.
2. **`OS_ADMIN_USER`** — defaults to `admin`.
3. **The administrator password** — see §3.3.

### 3.3 The one code change it needs

Today the dashboard accepts only `OS_ADMIN_PASSWORD_HASH`, which means running
`make hash-password` on a machine with Docker before deploying — the exact step
a one-button install exists to remove. It is also the step most likely to fail:
the `$$` escaping that Compose requires and Railway does not has already
produced a hash that matches no password.

Proposed: accept **`OS_ADMIN_PASSWORD`** as an alternative. At startup the
dashboard hashes it with bcrypt, keeps only the hash in memory, and logs a
warning recommending the hash form. Setting both is a startup error, like every
other malformed configuration. The trade-off — a plaintext secret in the
platform's variable store — is the same one `OS_SESSION_SECRET` and the
datastore passwords already make, and it must be recorded in
`implementation-decisions.md` together with the setting's entry in
`deploy/.env.example`.

### 3.4 What stays manual, and must be said so

- **Removing the origin's public domain.** A template cannot reach into a
  service it did not create. The template's description and the post-deploy
  page must make this the first instruction, not a footnote: until it is done,
  the deployment filters nothing.
- **Pointing the frontend at the proxy** and redeploying it (`VITE_API_URL` is
  baked in at build time).
- **CORS and CSRF origins** on the backend.

### 3.5 Done when

- The template deploys a working stack with no step outside Railway.
- `scripts/smoke.sh` passes against it unchanged.
- The source-address check of `deploy-railway.md` §6 shows real client
  addresses.
- `deploy-railway.md` opens with the template button and keeps the manual
  procedure as the reference for what the template does.

## 4. Hosts you own: one command, kept literal

On a VPS the original promise already holds; what is missing is the
installation *before* `make up-prod` — Docker, the clone, the secrets. This is
the highest-value phase because it covers every provider at once.

**Targets:** Hetzner Cloud, DigitalOcean Droplets, Akamai/Linode, Vultr, OVH,
AWS Lightsail and EC2, Google Compute Engine, Azure VMs — any Linux host with a
public address.

**Plan:**

- `scripts/install.sh`: checks for Docker and installs it if absent, clones the
  repository, generates `OS_SESSION_SECRET`, asks for the admin password and
  `OS_BACKEND_URL`, writes `deploy/.env` (with the `$$` escaping done for the
  user), and runs `make up-prod`. It must be idempotent and refuse to overwrite
  an existing `deploy/.env`.
- The same script works as **cloud-init user data**, so most providers' "create
  server" form becomes the single step.
- **Self-hosted PaaS on a VPS** (Coolify, Dokploy, CapRover) deploy a Compose
  file directly. `deploy/docker-compose.yml` should work unchanged; verify it on
  one of them and document any difference rather than forking the file.

**Settings:** none of the four in §2 change — clients connect directly, so
`OS_TRUSTED_PROXY` stays empty. If the user puts Cloudflare in front, that is
the managed-edge case again: `OS_REAL_IP_HEADER=CF-Connecting-IP` with
Cloudflare's published ranges as `OS_TRUSTED_PROXY`.

## 5. Managed platforms

Ordered by how close each comes to one step. Header names and address ranges in
this table are starting points from the platforms' documentation and **must be
measured** (§2) before a document is written.

| Platform | One-step mechanism | Private network | Datastores | Client-address header | Verdict |
|---|---|---|---|---|---|
| **Railway** | Template | `*.railway.internal`, IPv6-only | Catalogue Postgres, Redis | `X-Forwarded-For`, edge from `100.64.0.0/10` (measured) | Supported, template planned (§3) |
| **Render** | Blueprint (`render.yaml`) + "Deploy to Render" button | Private services on the internal network | Managed Postgres, Key Value (Redis-compatible) | To measure | Strong fit; Blueprint is a file in the repo |
| **DigitalOcean App Platform** | App spec + "Deploy to DigitalOcean" button | Internal service ports | Managed Postgres, managed Redis-compatible store | `do-connecting-ip` (to measure) | Strong fit |
| **Koyeb** | Service definition, deploy button | Private service mesh | Managed Postgres; Redis external | To measure | Possible; Redis is an external dependency |
| **Fly.io** | `fly.toml` per app; no single multi-app file | 6PN, `*.internal`, IPv6 | Managed Postgres; Redis via Upstash | `Fly-Client-IP` | Possible; needs a launch script for three apps |
| **Google Cloud Run** | None native for multi-service | Internal ingress + VPC connector | Cloud SQL, Memorystore | `X-Forwarded-For`, appended by Google's front end | Possible, heavy; Terraform territory |
| **AWS ECS / App Runner** | None native | VPC | RDS, ElastiCache | `X-Forwarded-For` via ALB | Out of scope for v1 — VPS path covers AWS |
| **Heroku** | `heroku.yml`, button | **Only in Private Spaces (paid)** | Postgres, Redis add-ons | `X-Forwarded-For`, appended by the router | Not supported outside Private Spaces: the engine would need a public address |
| **Vercel, Netlify, Cloudflare Pages** | — | — | — | — | Cannot host (§1) |

Notes on the rows that need more than a file:

- **Render and DigitalOcean** describe the whole stack declaratively, like a
  Railway template, but the description lives *in the repository*
  (`deploy/render.yaml`, `.do/deploy.template.yaml`). That makes them reviewable
  and testable in CI, which a template stored on the platform is not.
- **Fly.io** has no multi-app manifest. One `fly.toml` per service plus a
  `scripts/fly-launch.sh` that creates the three apps, attaches the datastores
  and sets the secrets is the closest to one step.
- **Heroku** routes traffic between dynos only through the public router unless
  the app is in a Private Space. A public engine answering unauthenticated
  verdicts is the one topology this project must not ship.

## 6. Phases

| Phase | Deliverable | Covers |
|---|---|---|
| 1 | `OS_ADMIN_PASSWORD` (§3.3) | Removes the off-platform step from every managed install |
| 2 | `scripts/install.sh` + cloud-init (§4) | Every VPS provider |
| 3 | Railway template (§3) | The deployment already in use |
| 4 | `deploy/render.yaml` and DigitalOcean app spec | Two one-button platforms, defined in the repo |
| 5 | Fly.io configuration and launch script | Fly.io |
| — | Cloud Run, ECS, Koyeb | On demand; the VPS path covers these providers meanwhile |
| — | Heroku outside Private Spaces, Vercel, Netlify, Cloudflare Pages | Not planned (§1, §5) |

Phase 1 comes first because every later phase depends on it: without it, each
one-button install still begins with "first, install Docker on another machine
and hash your password".

Each phase is done when:

1. its deployment passes `scripts/smoke.sh` unchanged;
2. the event list shows real, distinct client addresses — the check that
   proves `OS_TRUSTED_PROXY` and `OS_REAL_IP_HEADER` are right;
3. the engine has no public address, verified from outside;
4. a `docs/deploy-<platform>.md` and its `.es.md` translation exist, written
   from the measured values rather than the documented ones.
